# Structural & Architectural Issues

These are the things I would challenge you on in a seminar.

---

## 1. God-package problem (single namespace)

Everything lives in one conceptual layer:

* IO
* AST parsing
* analysis
* reporting
* persistence

This will not scale.

### Recommendation: layer the architecture

Create conceptual modules:

```
R/
  ast/
    walk_ast_for_pkgs.R
    extract_calls.R
    find_func_lines.R
    find_func_in_exprs.R

  scan/
    scan_definitions.R
    scan_dependencies.R
    list_r_files.R

  analysis/
    audit_inventory.R
    audit_exports.R
    detect_duplicates.R
    verify_migration.R
    map_internal_calls.R

  reporting/
    snapshot_audit.R
    compare_audits.R

  core/
    types.R        (audit_snapshot constructor)
    utils.R
```

Even if you keep files flat, structure mentally like this.

Why it matters:

* easier testing
* easier future plugins
* easier contributor onboarding
* clearer API boundary

---

## 2. Hidden global coupling via data frames

You pass around `inventory` data frames that gradually accumulate columns:

* `misplaced`
* `has_export_tag`
* `called_in_test`
* etc.

This is convenient but fragile.

### Risks:

* silent column name collisions
* order-dependent logic
* undocumented schema

### Improvement:

Define a schema:

```r
inventory columns:
  name
  type
  file
  misplaced
  called_in_test
  has_export_tag
  detached_tag
  in_namespace
  export_status
```

Then document it formally.

Even better:

Create constructor:

```r
new_inventory <- function(df) {
  structure(df, class = c("audit_inventory", class(df)))
}
```

And validate columns.

---

## 3. No explicit internal API contract

Functions like:

* `scan_definitions`
* `audit_inventory`
* `scan_dependencies`

are both internal and user-facing.

You should decide:

* which are **public API**
* which are **internal implementation**

Then:

* export only the public ones
* mark others `@noRd`

Right now the boundary is fuzzy.

---

## 4. Error handling strategy is inconsistent

Examples:

* `stop()` in some places
* silent `next` in others
* `tryCatch(..., NULL)` elsewhere

Pick a policy:

| Layer                  | Behavior  |
| ---------------------- | --------- |
| AST parsing            | soft-fail |
| Package root invalid   | hard-fail |
| Single file unreadable | warn      |
| Snapshot save fail     | hard-fail |

Then encode it consistently.

---

## 5. Performance: repeated parsing

You parse files repeatedly:

* in `scan_definitions`
* in `audit_exports`
* in `map_internal_calls`
* in `detect_duplicates`

This is O(N × analyses).

For large projects, this will hurt.

### Future design:

Introduce AST cache:

```r
parse_cache <- new.env()

get_ast <- function(file) {
  if (!exists(file, parse_cache)) {
    parse_cache[[file]] <- parse(file, keep.source = TRUE)
  }
  parse_cache[[file]]
}
```

Then reuse.

This alone could give 5–10× speedups.

---

## 6. Test coverage detection is naive (by design)

Current approach:

```r
grep function name in test files
```

This produces:

* false positives (mentioned but not called)
* false negatives (wrapped calls)

This is acceptable but should be **explicitly documented** as:

> lexical coverage heuristic

For academic honesty.
